# End-to-end test: one Discovery through all six skills

**Date:** 2026-10-26 · **Plugin:** ba-discovery 0.8.0 (branch `discovery-review/skill`) · **Project:** Test Project 4 (synthetic client "Northwind Dental", online appointment booking)

## How the test was run

- Claude ran every skill step by step from its `SKILL.md` in a cloud session, with the real Google Drive, Sheets, Docs, Gmail and Calendar connectors on the BA's account. Claude played the BA at each approval gate.
- The client material is synthetic: a one-page BRD with a planted contradiction, and a 15-minute kickoff transcript with a reversed decision and a changed requirement.
- **What this test is not:** a run by a BA in the Claude app with the plugin installed. That is still needed for the "Real run" item of the Definition of Done. Costs below come from the eval harness (Claude Sonnet 5.5, real per-run billing) and from estimates where stated, not from this session.

Workspace: [Test Project 4 — Discovery](https://drive.google.com/drive/folders/1qSTMeWElNMFd0idyDAK1FZJF-VWjMrPN)

## What went well

- **The chain works on real Drive files.** Each skill found the previous skill's output through `discovery.yaml` and the fixed sheet layouts; no ids had to be passed by hand.
- **Traceability end to end.** Every requirement, decision, answer and canvas entry carries a document section or a transcript timestamp. The History tab and the Updates tab show how the picture changed and which meetings are processed.
- **Judgement calls matched a careful BA.** Examples: the planted contradiction was found, a reversed decision was recorded as final, "next week" stayed vague, and an added target became a new requirement instead of overwriting a goal.
- **Nothing was written before approval**, and every write stayed inside the Discovery folder.
- **The wireframe is light and honest.** About 12 KB, neutral styles, every element tagged, the one invented element marked as an assumption.
- **Known connector issues are handled.** Paged listings were followed and the log insertion index worked first time. A Sheets read hit the quota and the Drive fallback was used.

## Findings

| # | Finding | Severity | Suggested fix |
|---|---|---|---|
| 1 | **Google Sheets per-minute quota.** 5 calls failed: 3 writes and 2 reads, when 4–6 Sheets calls ran in parallel. The skills say "retry once", and an immediate retry can fail again. | High: in a real run the BA sees errors and partial saves | Run Sheets calls one after another, not in parallel; on a quota error wait about 60 seconds, then retry. Put this in every skill's failure modes. |
| 2 | **The `00 README` template doesn't list `07 Prototype`.** | Low | Add the folder line to `templates-source`, rebuild `templates.json` |
| 3 | **"Where are we?" next step skips the client feedback step.** With the prototype current and no P1 questions, it says "ask me 'Is it complete?'" instead of "show the wireframe to the client in a feedback session". | Medium | Add a step to the next-step order: a prototype with no meeting after it → feedback session, then `discovery-docs-update` and `prototype` update |
| 4 | **Check 4 is unclear for requirements that live in another system.** REQ-014 (reception sees online bookings in Dentrix) needs no screen of ours. A spec that lists it under "Not shown as a screen" would fail the check. | Medium | Count a requirement as covered when the spec lists it, on a screen or under "Not shown" with a reason |
| 5 | **Risks without a priority are invisible to check 5.** R-001 (Dentrix licence may move the timeline) has no priority, because nobody said one, so it never counts as "High without owner". | Medium | `discovery-docs-update` asks the BA for a priority at the gate when a risk has none; or check 5 also lists open risks with no priority |
| 6 | **Several `discovery.yaml` files on one Drive.** With 3+ test projects, the search returns several records and pages them, so the skill has to ask which project every time. | Low | Name the record `discovery — {project}.yaml`, or search with `fullText contains '{project}'` when the BA names the project |
| 7 | **11 of 16 requirements are still Draft after the kickoff.** `discovery-docs-update` confirms only on explicit agreement, which is correct, but Drafts pile up. | Info | Fine as designed. The final check's "Also" line shows it; the BA can confirm in bulk in a review session |

## Price of the plugin per Discovery

API-equivalent cost with Claude Sonnet 5.5. A typical 3–4 week Discovery is assumed: 1 setup, 3 document batches, 8 meetings, 1 prototype plus 2 updates, a status check after each meeting, and 2 final checks. Each skill runs in its own chat.

| Skill | Runs | Cost per run with connectors (estimate) | Total |
|---|---|---|---|
| `discovery-setup` | 1 | $0.45: the plan run ($0.11) plus about 10k output tokens of template content and about 35 connector calls | $0.45 |
| `doc-analysis` | 3 | $0.20: real BRDs are 5–20 pages, not one | $0.60 |
| `workshop-summary` | 8 | $0.15: a 60-minute transcript is about 12k tokens | $1.20 |
| `discovery-docs-update` | 8 | $0.18: the transcript plus six growing sheets | $1.44 |
| `prototype` | 1 new + 2 updates | $0.25 new (map + build + save), $0.20 per update | $0.65 |
| `discovery-review` | 8 status + 2 final | $0.08 | $0.80 |
| **Total per Discovery** | | | **≈ $5 (range $4–7)** |

How the estimates were made: each measured eval cost, scaled up for real document sizes and connector overhead (tool definitions and larger tool results, about 1.5×). Sonnet 5.5 list price, used for the template output in setup: $2 per million input tokens, $10 per million output tokens, $0.20 per million cache reads ([Apidog](https://apidog.com/blog/claude-sonnet-5-5-pricing/), third-party; check the official price list). On a Claude subscription the same work counts against the plan's usage limits instead of costing dollars.

For scale: about $5 per Discovery is a few minutes of a BA's time, for work that takes a BA several hours by hand: setup, a document analysis, 8 summaries and emails, 8 document updates, a wireframe and a spec.

## Token optimization: suggestions

| # | Suggestion | Saves (estimate) | Effort |
|---|---|---|---|
| 1 | **Setup: copy master template files instead of rebuilding them.** Keep one master Doc or Sheet per template in a shared Drive folder, and create each file with Drive `copy_file`. The model no longer reads `templates.json` (9.5k tokens) or re-types it into tool calls (about 10k output tokens), and 9 Sheets writes disappear, which also avoids the quota. | about $0.25 per setup; the setup chat shrinks by half | Medium: needs a public template folder and a fallback when it isn't reachable |
| 2 | **Serialize Sheets calls and wait on a quota error.** Every failed call re-sends its whole payload; 5 failures in this run. | Avoids repeated payloads and broken runs | Low: a line in each skill |
| 3 | **One skill per chat.** Each tool result stays in the chat's context and is re-read on every later turn, so a long chat chaining several skills costs more than separate chats. The next-step line in each report can say "start a new chat for this". | 20–40% on long chats | Low |
| 4 | **Load only the connector tools a skill needs.** Already in every skill: "load exactly these by name". Keep it, and don't enable connectors the plugin doesn't use (each adds thousands of tokens to every turn). | Large, per turn | Done; document in README |
| 5 | **Prototype: emit the HTML once.** Today the wireframe is written into the chat and then again into the Drive file. Saving it first and showing the page from the saved file would save one copy. | about 4k output tokens (about $0.04) per build | Medium |
| 6 | **Use a smaller model for "Where are we?"** It only reads and counts, so a smaller model, for example Haiku, should do. | about 60–70% of that skill's cost | Low: a model hint in the skill, but it depends on what the app supports |
| 7 | **Sheets reads: keep `get_values` with exact ranges.** The Drive fallback (`read_file_content` on a Sheet) returned the canvas about twice over, as a table and again as column samples. | Small per call | Done; document as the fallback only |
| 8 | **Keep the per-skill budgets.** Every skill already has a token budget and an efficiency grader, so a change that makes a skill heavier fails the checks before it is merged. | Prevents regressions | Done |

## Suggestions for future enhancements

1. Fix findings 1–5 above, each with an eval case. The quota handling and the review's next step come first.
2. **Prototype publishing:** let the skill publish the wireframe as a shareable page directly, so the BA doesn't have to.
3. **Stakeholder Matrix:** fill it from the doc analysis and the meetings. It stays empty today, and the review could then check that key stakeholders were consulted.
4. **Bulk confirm:** a review session mode in `discovery-docs-update` for confirming several Draft requirements at once.
5. **Handover pack:** at the end, one Doc that links the canvas, register, decisions, open items and the latest prototype for the delivery team.
6. **BA test in the Claude app** (Definition of Done, item 4): install from the marketplace, repeat this script with a BA's own synthetic project, and record the result in each skill's README.
